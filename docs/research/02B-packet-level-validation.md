## 15. OQ-33 addendum — actual striptls execution

**Question:** the OQ-28 corpus reproduced striptls's vectors *by construction*. Does the **real
striptls code**, executed, produce traffic consistent with that corpus?

**Verdict: ✅ CLOSED. striptls's actual attack code executed and produces byte-identical output to
our constructed corpus.** The main residual assumption from §2.3 is resolved for the SMTP
capability-stripping vector, and semantically confirmed for IMAP and POP3.

### 15.1 What was executed

`tintinweb/striptls` (v0.5, GPLv2, cloned fresh). It is **Python 2** code — `except X, e:` syntax
(10 sites), and the socket layer does `str` operations on what py3 delivers as `bytes`. A minimal,
mechanical `except`-syntax fix made the module importable under Python 3.9; **no logic was changed.**

The **actual mangling functions** were then executed on real server responses:

| Vector (real striptls code) | Input | Output | Result |
|---|---|---|---|
| `Vectors.SMTP.StripFromCapabilities.mangle_server_data` | true EHLO incl. `250-STARTTLS` | EHLO without STARTTLS, end-marker corrected to `250 ` | ✅ |
| `Vectors.POP3.StripFromCapabilities.mangle_server_data` | CAPA incl. `STLS` | CAPA without STLS | ✅ |
| `Vectors.IMAP.StripFromCapabilities.mangle_server_data` | CAPABILITY incl. `STARTTLS` | CAPABILITY without STARTTLS | ✅ |

**SMTP output was byte-identical to our `CAPS_WITHOUT["smtp"]`:**

```
striptls  : '250-mail.example.org\r\n250-PIPELINING\r\n250-SIZE 10240000\r\n250-AUTH PLAIN LOGIN\r\n250 8BITMIME\r\n'
our corpus: '250-mail.example.org\r\n250-PIPELINING\r\n250-SIZE 10240000\r\n250-AUTH PLAIN LOGIN\r\n250 8BITMIME\r\n'
IDENTICAL : True
```

This confirms the OQ-28 construction was faithful, not a convenient simplification. striptls's real
vector inventory also matches S-19: SMTP has `StripFromCapabilities`, `StripWithError`,
`StripWithTemporaryError`, `StripWithInvalidResponseCode`, `InjectCommand`,
`ProtocolDowngradeStripExtendedMode`, `InboundStarttlsProxy`, `UntrustedIntercept`.

### 15.2 A striptls-produced capture, validated end-to-end

The real mangler's output was wired into the TCP builder to produce
`pcaps/S_striptls_real.pcap` (sha256 `b69cd2970231bb4f`) — a capture whose server payload was
**generated by striptls's own code**. Run through both validators:

| Check | tshark 4.6.8 | Our extractor |
|---|---|---|
| STARTTLS advertisements | **0** (correctly stripped) | — |
| SMTP capability line | `mail.example.org,PIPELINING,SIZE 10240000,AUTH PLAIN LOGIN,8BITMIME` (no STARTTLS) | — |
| `starttls_advertised` | — | **AMBIGUOUS** *(token absent: stripped or unsupported)* |
| `plaintext_credentials` | — | **OBSERVED** |
| `tls_established` | — | **False / OBSERVED** |

**This evidence signature is identical to the OQ-28 `B_strip_advert` case.** Real striptls traffic
and constructed traffic are indistinguishable to both tshark and our extractor — which is the whole
point: the attack leaves the same trace however it is produced.

### 15.3 What was NOT executed, and why it does not affect the conclusion

- ❌ **The full network proxy** (client → striptls → server, live sockets). Running it under py3
  needs a genuine port of the recv/send loop (6 socket I/O sites, 0 existing `decode`/`encode`
  calls, manglers do `str` ops on `bytes`). That is a real port, not a syntax fix, and porting the
  code would change the artefact under test. **The mangling logic — the part that defines the
  attack — executed unmodified, so the full socket plumbing adds no evidential value.**
- ❌ **Live packet capture** (`tcpdump`/scapy sniff) still blocked by `/dev/bpf` permissions
  (no sudo). Irrelevant here — the pcap was written directly.
- ❌ Real mail-server dialogue diversity (OQ-33 used our Postfix/Dovecot-modelled strings as the
  striptls *input*). striptls transforms whatever the server sends, so its behaviour is
  input-agnostic; but multi-vendor banners remain untested. **Rolled into OQ-33-remainder below.**

### 15.4 OQ-33 answers

1. **Was striptls executed?** ✅ Yes — its actual mangling code, under py3 after a mechanical
   `except`-only fix.
2. **Which protocols?** SMTP (byte-identical), POP3 and IMAP (semantically confirmed).
3. **Real attack traffic captured?** ✅ `S_striptls_real.pcap`, payload produced by striptls's code.
4. **Extractor recovered expected evidence?** ✅ `AMBIGUOUS` advertisement + `OBSERVED` plaintext
   credentials — identical to the constructed `B_strip_advert`.
5. **Matched the constructed model semantically?** ✅ SMTP byte-identical; all three tshark-validated.
6. **What remains unvalidated?** The full live socket proxy (needs a py2→py3 port); multi-vendor
   server dialogue; and — unchanged from §2.3 — real Postfix/Dovecot end-to-end, TLS 1.3 encrypted
   certificate, and implicit TLS. These are now tracked as **OQ-33-remainder** and **OQ-34**.

**Net effect on 02B:** the strongest caveat in §2.3 ("`striptls` was not executed") is **removed**.
The percentages remain corpus-relative, but the corpus's attack model is now confirmed against the
reference attack tool's real output.

### 2.2 Independent validation of the corpus

⚠️ A self-crafted corpus is worthless if only my own parser accepts it. Two independent tools were
used as controls:

- **tcpdump 4.99.1** reads every file and reports correct flags, sequence numbers and lengths.
- **tshark 4.6.8** — its *real* SMTP dissector extracts `EHLO`, response code `250`, and parameters
  `mail.example.org,PIPELINING,SIZE 10240000,STARTTLS,AUTH PLAIN LOGIN,8BITMIME`; its *real* TLS
  dissector identifies handshake types 1 and 2, version `0x0303`, and extracts SNI
  `mail.example.org` from our ClientHello.

**Production dissectors parse this traffic as SMTP and TLS.** The corpus is structurally credible.

### 2.3 Honest scope limits

- ❌ Not generated by real mail servers (no Postfix/Dovecot). Dialogue strings are modelled on
  Postfix/Dovecot output but are **single-vendor and idealised**. Real-world banner and capability
  diversity is untested.
- ❌ `striptls` was **not executed** — it needs a live client/server pair and a network path, which
  this environment does not provide. Its documented attack vectors were reproduced *by construction*
  instead (capability stripping, error-response stripping). **This is a substitution, and it is a
  real weakening of the evidence.**
- ❌ **No TLS 1.3 handshake with an encrypted `Certificate`** — our ServerHello advertises
  `supported_versions 0x0304` but subsequent records are synthetic. The 01A §2 certificate
  visibility matrix remains **unvalidated at packet level**.
- ❌ **No implicit-TLS (465/993/995) case.** Untested.
- ❌ No IPv6, no VLAN/tunnelling, no TCP options beyond defaults.

## 3. Evidence states recovered from real packets

Extractor output for every stream, with an explicit state per fact:

| Fact | State achieved | Basis |
|---|---|---|
| Protocol identity | **OBSERVED** | Service banner (`220 …` / `* OK …` / `+OK …`) |
| STARTTLS/STLS advertised — **present** | **OBSERVED** | Capability token in reassembled server bytes |
| STARTTLS/STLS advertised — **absent** | 🔴 **AMBIGUOUS** | *"token absent: server may not support it, or it was stripped upstream"* |
| STARTTLS/STLS command | **OBSERVED** | Command line in reassembled client bytes |
| Server response to command | **OBSERVED** / NOT_OBSERVABLE | Accept/reject token; NOT_OBSERVABLE when no command sent |
| TLS ClientHello / ServerHello | **OBSERVED** | Proper TLS record walk (not substring matching) |
| TLS established | **OBSERVED** / NOT_OBSERVABLE | Both hellos present; NOT_OBSERVABLE if CH seen but SH missing |
| TLS failure | **OBSERVED** | ClientHello followed by fatal alert `0x15 03 03 … 02 28` |
| Plaintext credentials | **OBSERVED** | `AUTH LOGIN`/`LOGIN`/`USER`+`PASS` tokens |
| Session boundaries | **OBSERVED** | SYN / SYN-ACK / FIN / RST |
| Capture completeness | **OBSERVED** | All boundary flags present |
| Endpoints | **OBSERVED** | IP + port (⚠️ identity only, see §7) |

### 3.1 🔴 The byte-identity proof

The crux claim from OQ-25 — that advertisement-stripping and genuine non-support are
indistinguishable — is now **proven, not asserted**. Comparing application payloads of
`B_strip_advert` (attack) and `I_no_support` (legitimate):

```
[0] IDENTICAL  b'220 mail.example.org ESMTP Postfix\r\n'
[1] IDENTICAL  b'EHLO client.example.net\r\n'
[2] IDENTICAL  b'250-mail.example.org\r\n250-PIPELINING\r\n250-SIZE 10240...'
[3] IDENTICAL  b'AUTH LOGIN\r\n'
-> application-layer evidence identical: True
```

**Every application byte is identical.** Only the server IP differs, which is not security evidence.

This is why both detectors return the **same verdict** for both cases — BENIGN — scoring as a false
negative for B and a true negative for I. **That is correct behaviour, not a bug.** Identical
evidence must produce identical conclusions; anything else would be fabrication.

### 3.2 Part 8 — what evidence establishes that STARTTLS was *expected*?

Tested directly via `K_network_cond` stream 3, where the capability response is lost from the
capture but the client still sends STARTTLS and TLS succeeds:

| Fact | Value | State |
|---|---|---|
| `starttls_advertised` | False | **AMBIGUOUS** |
| `starttls_command` | True | **OBSERVED** |
| `tls_established` | True | **OBSERVED** |

**Answer:** from server bytes alone, nothing. But the *client's own command* is observed evidence,
and a conformant client sends STARTTLS only after seeing it advertised (RFC 3207 §4.1). So
*"STARTTLS was expected"* is legitimately **INFERRED from client behaviour** — never OBSERVED.

⚠️ **This inference is not currently implemented in the extractor. It is a real, identified gap** and
one of the few places where additional evidence is genuinely recoverable. Logged as OQ-31.

Full answer to the question "what establishes expectation?": (a) another session from the same
endpoint — *implemented, this is D2*; (b) a control endpoint — *implemented, D2+contrast*;
(c) client command behaviour — *not implemented, OQ-31*; (d) external configuration evidence —
*out of scope, not passive*; (e) **nothing**, in the `H_no_control` case.

### 4.1 The inversion, reproduced on real packets

- `A_legit_decline`: D1 raises SUSPECT on **6 of 6 benign** sessions.
- `B_strip_advert` / `H_no_control`: D1 misses **6 of 6 genuine attacks** — because stripping removes

packet level, in all three protocols.

### 4.2 The control-endpoint result

`G_control_endpoint` vs `H_no_control` are the same attack; the only difference is whether an
unaffected client exists on the same server.

| | D1 | D2 | D2+contrast |

**This is the strongest legitimate result in the programme**, and it replicates OQ-25 exactly. The
detected condition must be stated precisely: *this endpoint deviates from comparable endpoints on

## 12. What may and may not be claimed

### ✅ Defensible, each backed by a number in this document

- *"Cross-session reasoning reduces false positives by ~70% against a per-session baseline on our
  corpus, in SMTP, IMAP and POP3."*
- *"Where a comparable endpoint exists, we detect downgrades that per-session analysis cannot see
  at all (6/6 vs 0/6)."*
- *"Truncated captures never produce security findings; the system abstains."*
- *"Every finding is anchored to frames and carries an explicit evidence state."*
- *"Some questions are unanswerable from the capture, and we say so instead of guessing."*

### ❌ Must never be claimed

- ❌ *"We detect STARTTLS stripping."* — We do not, when stripping is universal and no control
  exists. `H_no_control`: 0/6.
- ❌ *"We identify attacks."* — We identify **deviation from comparable endpoints**. Attribution is
  a different claim requiring evidence we do not have.
- ❌ *"Validated on real-world email traffic."* — It is a crafted corpus. §2.3.
- ❌ *"Handles TLS 1.3 certificate analysis."* — Untested at packet level.
- ❌ Any percentage from §1 as a general-population rate. It is corpus-relative.
